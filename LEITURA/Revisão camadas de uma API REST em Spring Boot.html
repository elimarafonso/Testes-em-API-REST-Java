Revisão rápida: camadas de uma API REST em Spring Boot

Cada card explica quando usar o recurso, como ele funciona por baixo dos panos, com qual outra classe ele se relaciona e o resultado esperado ao rodar. Use a busca para filtrar por anotação ou palavra-chave, ou navegue pelo menu lateral.

Base de versões (ago/2026): Java 17+ · Spring Boot 3.5.x (LTS) ou 4.0/4.1.x (linha atual) — as anotações e o código desta página valem para as duas. Números de versão de dependências (springdoc, jjwt, Flyway...) mudam com frequência: trate os exemplos abaixo como ponto de partida e confira sempre a versão mais recente no Maven Central antes de fixar no seu pom.xml.
Controller

Camada de entrada HTTP

Recebe a requisição, delega ao Service e devolve a resposta. Não deve conter regra de negócio nem acesso direto ao banco. Todos os exemplos abaixo pertencem a uma mesma classe, ProdutoController, exceto onde indicado (sub-recursos de avaliação).

VerboAnotação SpringIdempotente?Uso típico no dia a dia
GET@GetMappingSimBuscar/listar recursos, sem alterar estado
POST@PostMappingNãoCriar um novo recurso ou disparar uma ação
PUT@PutMappingSimSubstituir por completo um recurso existente
PATCH@PatchMappingDependeAtualizar parcialmente um recurso (poucos campos)
DELETE@DeleteMappingSimRemover um recurso (único ou em lote)

Anotação base da classe

Quando usar: em toda classe que expõe endpoints HTTP — é o ponto de entrada da API. Como funciona: @RestController registra a classe como um bean do Spring e serializa automaticamente o retorno de cada método para JSON (via Jackson), sem precisar anotar método por método com @ResponseBody. @RequestMapping("/api/produtos") define o prefixo comum: todo endpoint declarado dentro da classe herda esse caminho. Relacionado a: o construtor recebe ProdutoService por injeção de dependência — é para lá que este Controller delega toda a lógica de negócio (ver seção Service).

@RestController
@RequestMapping("/api/produtos") // prefixo de todos os endpoints
public class ProdutoController {
    private final ProdutoService service; // injeção via construtor
}
Resultado esperado

Ao subir a aplicação, o Spring registra automaticamente todas as rotas /api/produtos/* mapeadas nesta classe — nenhuma configuração manual de rota é necessária.

GET Leitura de recursos

GET com parâmetro de caminho

Quando usar: para buscar um único recurso identificado por um valor na própria URL, como um id. Como funciona: o Spring extrai o trecho {id} da URL, converte para o tipo declarado (Long) e injeta como argumento do método via @PathVariable. Relacionado a: este método chama service.buscarPorId(id) em ProdutoService, que por sua vez consulta o ProdutoRepository.

@GetMapping("/{id}")
public ResponseEntity<ProdutoDTO> buscar(@PathVariable Long id) {
    return ResponseEntity.ok(service.buscarPorId(id));
}
Resultado esperado

GET /api/produtos/7 retorna 200 OK com o JSON do produto de id 7. Se o id não existir, o Service lança ProdutoNaoEncontradoException (seção Exceções), resultando em 404.

GET com parâmetro de query (opcional)

Quando usar: em listagens com filtro opcional, sem precisar criar uma URL separada para cada tipo de busca. Como funciona: @RequestParam lê o parâmetro nome da query string (?nome=...); como required = false, a requisição funciona normalmente mesmo sem esse parâmetro (chega como null). Relacionado a: decide dinamicamente entre listarTodos() e buscarPorNome(nome), ambos em ProdutoService.

@GetMapping
public List<ProdutoDTO> listar(
        @RequestParam(required = false) String nome) {
    return nome == null ? service.listarTodos() : service.buscarPorNome(nome);
}
Resultado esperado

GET /api/produtos retorna todos os produtos; GET /api/produtos?nome=mouse retorna 200 OK só com os produtos cujo nome contém "mouse" (ignorando maiúsculas/minúsculas).

GET de sub-recurso (recurso aninhado)

Quando usar: quando o recurso pertence claramente a outro (ex: avaliações de um produto) — é mais comum no dia a dia do que parece, sempre que há relação 1:N navegável pela API. Como funciona: o path combina os dois níveis, /{produtoId}/avaliacoes; o Spring extrai o produtoId como @PathVariable normalmente, e o Service usa esse id para filtrar. Relacionado a: chama service.listarAvaliacoesDoProduto(produtoId), que internamente pode usar um AvaliacaoRepository com um método como findByProdutoId(Long produtoId).

@GetMapping("/{produtoId}/avaliacoes")
public List<AvaliacaoDTO> listarAvaliacoes(@PathVariable Long produtoId) {
    return service.listarAvaliacoesDoProduto(produtoId);
}
Resultado esperado

GET /api/produtos/7/avaliacoes retorna 200 OK com a lista de avaliações do produto 7. Se o produto não existir, o Service deve validar isso antes de buscar as avaliações, lançando ProdutoNaoEncontradoException (→ 404).

POST Criação de recursos

POST com corpo validado

Quando usar: para criar um novo recurso a partir de dados enviados pelo cliente no corpo da requisição. Como funciona: @RequestBody desserializa o JSON recebido para um ProdutoRequestDTO (seção DTO); @Valid dispara as validações Bean Validation declaradas nesse DTO antes mesmo do corpo do método rodar. Relacionado a: delega a ProdutoService.criar(dto), que persiste via ProdutoRepository e devolve um ProdutoDTO de resposta.

@PostMapping
public ResponseEntity<ProdutoDTO> criar(@Valid @RequestBody ProdutoRequestDTO dto) {
    ProdutoDTO criado = service.criar(dto);
    return ResponseEntity.status(HttpStatus.CREATED).body(criado); // 201
}
Resultado esperado

Uma requisição válida retorna 201 Created com o produto criado (incluindo o id gerado). Um campo inválido (ex: nome em branco) nunca chega a executar este método — o Spring já responde 400 Bad Request antes, por causa do @Valid.

POST em sub-recurso

Quando usar: para criar um recurso que só existe no contexto de outro — não faz sentido uma avaliação sem produto. Como funciona: igual ao POST comum, mas o path inclui o id do "pai" (produtoId), que é repassado ao Service junto com o corpo validado. Relacionado a: service.avaliarProduto(produtoId, dto), que confirma que o produto existe antes de persistir a nova Avaliacao vinculada a ele.

@PostMapping("/{produtoId}/avaliacoes")
public ResponseEntity<AvaliacaoDTO> avaliar(
        @PathVariable Long produtoId, @Valid @RequestBody AvaliacaoRequestDTO dto) {
    AvaliacaoDTO criada = service.avaliarProduto(produtoId, dto);
    return ResponseEntity.status(HttpStatus.CREATED).body(criada); // 201
}
Resultado esperado

POST /api/produtos/7/avaliacoes com corpo válido retorna 201 Created com a avaliação criada, já vinculada ao produto 7.

PUT Substituição completa

PUT (atualização completa)

Quando usar: para substituir por completo os dados de um recurso já existente, identificado pelo id na URL. Como funciona: combina @PathVariable (identifica o recurso) com @RequestBody @Valid (o novo estado completo). Relacionado a: delega a ProdutoService.atualizar(id, dto), que busca a entidade existente no ProdutoRepository e sobrescreve seus campos.

@PutMapping("/{id}")
public ResponseEntity<ProdutoDTO> atualizar(
        @PathVariable Long id, @Valid @RequestBody ProdutoRequestDTO dto) {
    return ResponseEntity.ok(service.atualizar(id, dto));
}
Resultado esperado

Retorna 200 OK com o produto atualizado. Se o id não existir, o mesmo ProdutoNaoEncontradoException do GET por id é lançado, resultando em 404.

PATCH Atualização parcial

PATCH com DTO parcial (mais comum no dia a dia)

Quando usar: quando o cliente quer alterar só alguns campos, sem reenviar o recurso inteiro (ex: só o preço, em uma tela de "editar preço"). Como funciona: o DTO de patch tem todos os campos opcionais (podem vir null); o Service aplica apenas os campos que chegaram preenchidos, mantendo os demais como estavam na entidade. Relacionado a: diferente do ProdutoRequestDTO usado no POST/PUT, este é um DTO próprio — as anotações de validação (@NotBlank, etc.) geralmente não fazem sentido aqui, já que ausência de campo é esperada.

// DTO com campos opcionais — nada é @NotNull/@NotBlank
public record ProdutoPatchDTO(String nome, BigDecimal preco) {}

@PatchMapping("/{id}")
public ResponseEntity<ProdutoDTO> atualizarParcial(
        @PathVariable Long id, @RequestBody ProdutoPatchDTO patch) {
    return ResponseEntity.ok(service.atualizarParcial(id, patch));
}

// No Service: aplica só o que veio preenchido
public ProdutoDTO atualizarParcial(Long id, ProdutoPatchDTO patch) {
    Produto produto = buscarOuLancar(id);
    if (patch.nome() != null)  produto.setNome(patch.nome());
    if (patch.preco() != null) produto.setPreco(patch.preco());
    return ProdutoDTO.fromEntity(produto); // @Transactional cuida do UPDATE
}
Resultado esperado

PATCH /api/produtos/7 com corpo {"preco": 199.90} altera só o preço e devolve 200 OK com o produto completo atualizado — o nome permanece o que já estava salvo.

PATCH com JSON Merge Patch (ObjectMapper)

Quando usar: quando você quer um PATCH genérico, sem criar um DTO parcial para cada entidade, seguindo o padrão HTTP oficial de merge patch. Como funciona: o cliente envia só os campos que quer mudar, com Content-Type: application/merge-patch+json (RFC 7396); o Spring injeta o corpo cru como JsonNode, e ObjectMapper.readerForUpdating(...) aplica esse JSON por cima da entidade já carregada, sobrescrevendo apenas os campos presentes. Relacionado a: usa o ObjectMapper do próprio Spring (já configurado para Jackson), injetado via construtor no Controller.

@PatchMapping(path = "/{id}", consumes = "application/merge-patch+json")
public ResponseEntity<ProdutoDTO> mergePatch(
        @PathVariable Long id, @RequestBody JsonNode patch) throws IOException {
    Produto existente = service.buscarEntidadePorId(id);
    Produto atualizado = objectMapper.readerForUpdating(existente).readValue(patch);
    return ResponseEntity.ok(service.salvar(atualizado));
}
Resultado esperado

Um PATCH com {"preco": 199.90} e o header application/merge-patch+json atualiza só esse campo na entidade em memória antes de salvar — o restante do objeto permanece intacto, mesmo sem um DTO específico para cada combinação de campos.

DELETE Remoção de recursos

DELETE

Quando usar: para remover permanentemente um recurso. Como funciona: recebe o id pela URL e delega a service.deletar(id); em caso de sucesso, devolve uma resposta sem corpo. Relacionado a: ProdutoService.deletar, que também usa o padrão "buscar ou lançar exceção" (seção Service) antes de remover.

@DeleteMapping("/{id}")
public ResponseEntity<Void> deletar(@PathVariable Long id) {
    service.deletar(id);
    return ResponseEntity.noContent().build(); // 204
}
Resultado esperado

204 No Content, sem corpo de resposta. Chamar DELETE de novo sobre o mesmo id já removido normalmente devolve 404, pois o recurso não existe mais para o Service encontrar.

DELETE em lote (múltiplos ids)

Quando usar: quando a tela permite selecionar vários itens e excluir de uma vez (ex: uma tabela com checkboxes) — evitar N requisições separadas. Como funciona: os ids chegam como lista na query string via @RequestParam; o Service delega ao JpaRepository.deleteAllById(ids), que remove todos em uma única operação. Relacionado a: ainda é considerado idempotente — repetir a mesma chamada com os mesmos ids não causa efeito colateral adicional, pois os ids já removidos simplesmente são ignorados.

@DeleteMapping
public ResponseEntity<Void> deletarEmLote(@RequestParam List<Long> ids) {
    service.deletarEmLote(ids);
    return ResponseEntity.noContent().build(); // 204
}

// No Service:
public void deletarEmLote(List<Long> ids) {
    produtoRepository.deleteAllById(ids); // vem pronto no JpaRepository
}
Resultado esperado

DELETE /api/produtos?ids=1,2,3 remove os três produtos de uma vez e retorna 204 No Content. Se algum id não existir, o comportamento padrão do Spring Data é simplesmente ignorá-lo — vale decidir explicitamente se isso é aceitável para o seu caso de uso.

Extra Controle fino da resposta

Paginação com Pageable

Quando usar: em listagens que podem crescer muito (centenas ou milhares de registros), evitando devolver tudo de uma vez. Como funciona: o Spring interpreta os parâmetros page, size e sort da própria query string e monta um Pageable automaticamente — não é preciso ler esses parâmetros manualmente. Relacionado a: repassado ao ProdutoService, que passa direto para um método do ProdutoRepository que retorna Page<Produto> (ver seção Repository, card "Paginação nativa").

@GetMapping("/paginado")
public Page<ProdutoDTO> listarPaginado(
        @PageableDefault(size = 20, sort = "nome") Pageable pageable) {
    return service.listarPaginado(pageable);
}
// chamada: GET /api/produtos/paginado?page=0&size=20&sort=preco,desc
Resultado esperado

Retorna 200 OK com um objeto Page contendo os 20 produtos mais caros da primeira página, além de metadados como totalElements e totalPages.

ResponseEntity com status customizado

Quando usar: quando a resposta automática (200/201/204) não é suficiente e você precisa de um status HTTP específico, um header customizado, ou controle total sobre o corpo. Como funciona: ResponseEntity é um wrapper genérico que representa a resposta HTTP inteira — status, headers e corpo — deixando explícito o que a API devolve, em vez de depender de convenções implícitas.

return ResponseEntity
        .status(HttpStatus.CONFLICT)   // 409
        .header("X-Motivo", "duplicado")
        .body(erroDTO);
Resultado esperado

O cliente recebe 409 Conflict, com o header X-Motivo: duplicado e o corpo JSON de erroDTO — útil, por exemplo, ao tentar criar um produto com nome já existente.

  • Controller "magro": nada de lógica de negócio aqui — apenas orquestra a chamada ao Service.
  • URLs com substantivo no plural (/produtos), nunca verbos (/criarProduto ❌).
  • Sempre devolva o status HTTP correto (201 ao criar, 204 ao deletar, 404 quando não encontrado).
  • Versione a API quando fizer mudanças que quebram compatibilidade: /api/v1/produtos.
  • Nunca retorne a Entity diretamente — sempre um DTO.
  • PUT substitui o recurso inteiro (o cliente deve enviar todos os campos); PATCH altera só o que foi enviado — escolha com base no que a tela do cliente realmente envia, não por hábito.
  • Considere "soft delete" (uma coluna ativo/deletadoEm) em vez de exclusão física quando o histórico do recurso importa — nesse caso, DELETE vira um UPDATE internamente, mas a API continua expondo o verbo DELETE.
  • Endpoints de exclusão em lote continuam idempotentes: repetir a chamada com os mesmos ids não deve gerar erro, mesmo que parte deles já tenha sido removida antes.
  • Sub-recursos (/produtos/{id}/avaliacoes) só fazem sentido quando o filho não existe sem o pai — caso contrário, prefira um recurso de primeiro nível com filtro (/avaliacoes?produtoId=7).
Entity

Mapeamento objeto-relacional (JPA)

Classe Java que representa uma tabela do banco. Cada instância = uma linha. É a classe Produto que o ProdutoRepository (seção Repository) manipula diretamente.

Estrutura mínima

Quando usar: em toda classe que deve ser persistida como uma tabela do banco. Como funciona: @Entity registra a classe no contexto de persistência do JPA/Hibernate; @Table(name=...) define o nome físico da tabela (sem ela, o Hibernate usaria o nome da classe); @Id marca a chave primária e @GeneratedValue(strategy = IDENTITY) delega ao próprio banco a geração do valor (equivalente a AUTO_INCREMENT/SERIAL). Relacionado a: consumida diretamente por ProdutoRepository extends JpaRepository<Produto, Long> — nunca deve ser exposta como resposta da API (para isso existe o ProdutoDTO, seção DTO).

@Entity
@Table(name = "produtos")
public class Produto {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String nome;
}
Resultado esperado

O Hibernate cria (ou valida, dependendo de ddl-auto) uma tabela produtos com colunas id (chave primária, auto-incremento) e nome (VARCHAR(120), NOT NULL).

Relacionamento N:1 (@ManyToOne)

Quando usar: quando muitos registros de uma entidade apontam para um único registro de outra — aqui, vários Produto pertencem a uma mesma Categoria. Como funciona: @JoinColumn define a coluna de chave estrangeira (categoria_id) na tabela produtos; fetch = FetchType.LAZY faz o Hibernate não carregar a Categoria do banco até que o código realmente acesse produto.getCategoria(), evitando consultas desnecessárias.

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "categoria_id")
private Categoria categoria;
Resultado esperado

A tabela produtos ganha uma coluna categoria_id referenciando categorias(id). Buscar um produto não dispara automaticamente um SELECT na categoria — só quando ela é efetivamente acessada no código.

Relacionamento 1:N (@OneToMany)

Quando usar: no lado "um" de uma relação um-para-muitos, para navegar de Categoria até a lista de Produto associados. Como funciona: mappedBy = "categoria" informa que quem controla o relacionamento é o atributo categoria lá na classe Produto — evita que o Hibernate crie uma tabela de junção desnecessária. cascade = CascadeType.ALL propaga operações (salvar, deletar) da Categoria para seus produtos; orphanRemoval = true remove do banco um produto retirado dessa lista em memória.

@OneToMany(mappedBy = "categoria", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Produto> produtos = new ArrayList<>();
Resultado esperado

Deletar uma Categoria com cascade ALL deleta automaticamente todos os produtos associados a ela — use com cuidado em relações reais de negócio.

Relacionamento N:N (@ManyToMany)

Quando usar: quando registros de ambos os lados podem se relacionar livremente — um Produto pode ter várias Tag, e uma Tag pode estar em vários produtos. Como funciona: @JoinTable cria (ou mapeia) uma tabela intermediária com duas colunas de chave estrangeira, uma para cada lado.

@ManyToMany
@JoinTable(name = "produto_tag",
    joinColumns = @JoinColumn(name = "produto_id"),
    inverseJoinColumns = @JoinColumn(name = "tag_id"))
private Set<Tag> tags = new HashSet<>();
Resultado esperado

O banco ganha uma tabela produto_tag(produto_id, tag_id); chamar produto.getTags() dispara um JOIN implícito via essa tabela intermediária.

Enum mapeado

Quando usar: para campos que representam um conjunto fixo de estados, como o status de um pedido. Como funciona: EnumType.STRING instrui o Hibernate a gravar o nome textual da constante (ex: "ABERTO") na coluna; a alternativa, EnumType.ORDINAL, gravaria a posição numérica (0, 1, 2...), que quebra silenciosamente se a ordem dos valores do enum mudar no futuro.

@Enumerated(EnumType.STRING)
@Column(nullable = false)
private StatusPedido status; // ex: ABERTO, PAGO, CANCELADO
Resultado esperado

StatusPedido.ABERTO é salvo no banco como a string 'ABERTO', legível diretamente numa consulta SQL manual — diferente do frágil '0' que ORDINAL gravaria.

Callbacks de ciclo de vida

Quando usar: para preencher automaticamente campos de auditoria simples (data de criação/atualização) sem lembrar de setá-los manualmente em cada Service. Como funciona: o Hibernate invoca esses métodos nos momentos certos do ciclo de vida da entidade — @PrePersist logo antes do primeiro INSERT, @PreUpdate logo antes de qualquer UPDATE subsequente.

@PrePersist
public void aoCriar() { this.criadoEm = LocalDateTime.now(); }

@PreUpdate
public void aoAtualizar() { this.atualizadoEm = LocalDateTime.now(); }
Resultado esperado

Ao chamar produtoRepository.save(novoProduto) pela primeira vez, criadoEm é preenchido automaticamente com o instante atual, sem que o ProdutoService precise fazer isso.

  • Nunca exponha a Entity direto na API — use sempre um DTO (evita acoplamento e vazamento de dados).
  • Prefira FetchType.LAZY por padrão; use EAGER só quando necessário.
  • Cuidado com equals()/hashCode() em Entities com relacionamentos — prefira basear só no id.
  • Use BigDecimal para valores monetários, nunca double/float.
  • Em produção, gerencie o schema com Flyway/Liquibase — nunca ddl-auto=update.
Repository

Acesso a dados (Spring Data JPA)

Interfaces que o Spring implementa automaticamente. Sem SQL manual na maioria dos casos. Toda a seção gira em torno de ProdutoRepository, injetado diretamente no ProdutoService.

Interface base

Quando usar: é o ponto de partida da camada de persistência — uma interface para cada Entity que precisa de acesso a dados. Como funciona: ao estender JpaRepository<Produto, Long>, o Spring Data JPA gera automaticamente, em tempo de execução, uma implementação com métodos prontos (save, findById, findAll, deleteById, count...) — você nunca escreve essa implementação. Relacionado a: injetada diretamente no ProdutoService via construtor (seção Service).

public interface ProdutoRepository extends JpaRepository<Produto, Long> {
    //                                        ^ Entity        ^ tipo do id
}
Resultado esperado

Sem escrever nenhum código de implementação, produtoRepository.save(produto) já executa um INSERT ou UPDATE, e findById(5L) já executa um SELECT ... WHERE id = 5.

Query methods (nome do método vira SQL)

Quando usar: para consultas simples e específicas, sem precisar escrever SQL/JPQL manualmente. Como funciona: o Spring Data JPA interpreta o nome do método em tempo de inicialização (convenção findBy + atributo + operador opcional) e gera a query correspondente automaticamente.

List<Produto> findByNomeContainingIgnoreCase(String nome); // LIKE %nome%
List<Produto> findByPrecoLessThanEqual(BigDecimal preco);   // preco <= ?
boolean existsByNome(String nome);
long countByQuantidadeEstoque(Integer quantidade);
List<Produto> findTop5ByOrderByPrecoDesc();
Resultado esperado

Chamar findByNomeContainingIgnoreCase("mouse") executa o equivalente a SELECT * FROM produtos WHERE UPPER(nome) LIKE UPPER('%mouse%') e devolve a lista correspondente — vazia, se nada for encontrado (nunca null).

Consulta customizada com @Query (JPQL)

Quando usar: quando a lógica da consulta é complexa demais para caber no nome do método (múltiplas condições, agregações). Como funciona: a query é escrita em JPQL — parecida com SQL, mas opera sobre entidades e atributos Java (Produto, p.preco) em vez de tabelas e colunas; @Param liga :min/:max do JPQL aos parâmetros do método.

@Query("SELECT p FROM Produto p WHERE p.preco BETWEEN :min AND :max")
List<Produto> buscarPorFaixaDePreco(@Param("min") BigDecimal min,
                                     @Param("max") BigDecimal max);
Resultado esperado

buscarPorFaixaDePreco(10, 50) retorna todos os produtos com preço entre 10 e 50 (inclusive), traduzido pelo Hibernate para SQL na hora da execução.

Consulta SQL nativa

Quando usar: para consultas que dependem de recursos específicos do banco que a JPQL não cobre. Como funciona: nativeQuery = true diz ao Spring para executar a string exatamente como SQL puro no banco configurado, sem passar pela tradução JPQL — o retorno ainda é mapeado para objetos Produto normalmente.

@Query(value = "SELECT * FROM produtos WHERE estoque = 0", nativeQuery = true)
List<Produto> buscarSemEstoque();
Resultado esperado

buscarSemEstoque() executa literalmente esse SQL no banco e devolve a lista de Produto correspondente.

UPDATE/DELETE customizado

Quando usar: para alterações em massa que não fazem sentido carregar entidade por entidade em memória. Como funciona: @Modifying avisa que essa @Query altera dados (não é um SELECT); por isso precisa rodar dentro de uma transação explícita (@Transactional), já que o Hibernate não gerencia esse UPDATE pelo ciclo normal de uma entidade gerenciada.

@Modifying
@Transactional
@Query("UPDATE Produto p SET p.quantidadeEstoque = 0 WHERE p.id = :id")
void zerarEstoque(@Param("id") Long id);
Resultado esperado

zerarEstoque(10L) executa um UPDATE produtos SET quantidade_estoque = 0 WHERE id = 10 direto no banco, sem buscar o Produto primeiro.

Paginação nativa

Quando usar: sempre que uma query personalizada também precisar de paginação, não só findAll(). Como funciona: basta acrescentar um parâmetro Pageable e trocar o retorno para Page<Produto> — o Spring Data JPA gera automaticamente o LIMIT/OFFSET e o COUNT para o total de páginas. Relacionado a: chamado a partir do ProdutoController (seção Controller, card "Paginação com Pageable").

Page<Produto> findByNomeContainingIgnoreCase(String nome, Pageable pageable);
Resultado esperado

Devolve só a fatia de resultados pedida, mais metadados como totalElements — sem carregar a tabela inteira em memória.

  • Repository deve ser "burro": só consulta dados, nunca contém regra de negócio.
  • Prefira query methods para casos simples; @Query para casos complexos.
  • Use projeções (interfaces ou DTOs) quando não precisar da Entity inteira — melhora performance.
  • Sempre pagine listagens que podem crescer muito.
Service

Regras de negócio

Orquestra chamadas ao Repository e aplica as regras da aplicação. Não conhece HTTP. Classe central: ProdutoService, chamada pelo ProdutoController e consumindo o ProdutoRepository.

Injeção de dependência via construtor

Quando usar: em toda classe @Service, e de forma geral em qualquer bean do Spring que dependa de outro bean. Como funciona: @RequiredArgsConstructor (Lombok) gera automaticamente um construtor recebendo todo atributo final; o Spring detecta esse construtor e injeta a implementação de ProdutoRepository no momento em que cria o bean — sem precisar de @Autowired explícito.

@Service
@RequiredArgsConstructor
public class ProdutoService {
    private final ProdutoRepository repository; // nunca @Autowired em campo
}
Resultado esperado

Ao subir a aplicação, o Spring instancia um único ProdutoService (escopo singleton por padrão) já com o repositório pronto; em testes unitários, esse mesmo construtor permite passar um mock manualmente (seção Testes).

Transação de escrita

Quando usar: em qualquer método que grave, altere ou remova dados. Como funciona: @Transactional abre uma transação antes do método rodar e só faz commit se ele terminar sem lançar exceção; se algo falhar no meio do caminho, o Spring desfaz (rollback) tudo automaticamente, evitando dados parcialmente salvos.

@Transactional
public ProdutoDTO criar(ProdutoRequestDTO dto) {
    Produto salvo = repository.save(toEntity(dto));
    return ProdutoDTO.fromEntity(salvo);
}
Resultado esperado

Se repository.save(...) lançar uma exceção, nenhuma linha é gravada — tudo ou nada. Em caso de sucesso, devolve o ProdutoDTO já com o id gerado pelo banco.

Transação de leitura (otimizada)

Quando usar: em métodos que só consultam dados, sem alterar nada — a maioria dos métodos de listagem/busca. Como funciona: readOnly = true é uma dica para o Hibernate e o driver do banco otimizarem a transação (ex: pulando verificações de dirty-checking desnecessárias), reduzindo o overhead de uma consulta simples.

@Transactional(readOnly = true)
public List<ProdutoDTO> listarTodos() {
    return repository.findAll().stream().map(ProdutoDTO::fromEntity).toList();
}
Resultado esperado

Devolve a lista completa de ProdutoDTO convertida a partir das entidades do repositório, sem efeito colateral no banco, mesmo chamado repetidas vezes.

Buscar ou lançar exceção de negócio

Quando usar: sempre que uma operação depende de um recurso que pode não existir — evita duplicar a checagem em vários métodos. Como funciona: findById(id) devolve um Optional<Produto>; orElseThrow dispara a ProdutoNaoEncontradoException customizada (seção Exceções) quando o Optional está vazio, interrompendo o fluxo antes de qualquer outro código rodar. Relacionado a: chamado por buscarPorId, atualizar e deletar do próprio ProdutoService.

private Produto buscarOuFalhar(Long id) {
    return repository.findById(id)
            .orElseThrow(() -> new ProdutoNaoEncontradoException(id));
}
Resultado esperado

Se o id não existir, a exceção sobe até o GlobalExceptionHandler, que converte automaticamente em uma resposta HTTP 404 — o restante do método nunca chega a executar.

  • Toda regra de negócio mora aqui — não no Controller nem no Repository.
  • Service não deve conhecer detalhes HTTP (nada de HttpServletRequest, ResponseEntity aqui).
  • Um Service pode ser reaproveitado por múltiplos Controllers (REST, mensageria, jobs...).
  • Métodos pequenos e com um propósito único facilitam testes unitários com mocks.
DTO

Data Transfer Object

Desacopla o contrato da API (o que trafega) do modelo interno do banco. Usados pelo ProdutoController como tipo de entrada/saída, convertidos de/para Produto (Entity) dentro do ProdutoService.

DTO de requisição (record)

Quando usar: como tipo do parâmetro @RequestBody em endpoints POST/PUT — representa exatamente os campos que o cliente pode enviar. Como funciona: por ser um record, o Java gera automaticamente construtor, getters (nome(), preco()...), equals/hashCode e um objeto imutável; as anotações de Bean Validation (seção Validação) ficam direto nos parâmetros e são checadas quando o Controller usa @Valid.

public record ProdutoRequestDTO(
        @NotBlank String nome,
        @NotNull @PositiveOrZero BigDecimal preco) {}
Resultado esperado

Um JSON {"nome":"Mouse","preco":59.9} é desserializado pelo Jackson em new ProdutoRequestDTO("Mouse", new BigDecimal("59.9")); um preco negativo faz a validação falhar antes de qualquer código do Controller rodar.

DTO de resposta + mapeamento

Quando usar: como tipo de retorno de qualquer endpoint que devolve dados de um Produto ao cliente. Como funciona: fromEntity(Produto p) é um método estático de fábrica que centraliza, em um único lugar, a conversão de Produto (Entity) para ProdutoDTO (contrato público) — evita repetir esse mapeamento campo a campo em vários pontos do código. Relacionado a: chamado pelo ProdutoService em todos os métodos que retornam dados.

public record ProdutoDTO(Long id, String nome, BigDecimal preco) {
    public static ProdutoDTO fromEntity(Produto p) {
        return new ProdutoDTO(p.getId(), p.getNome(), p.getPreco());
    }
}
Resultado esperado

O Controller nunca vê um objeto Produto, só ProdutoDTO, serializado pelo Jackson como {"id":1,"nome":"Mouse","preco":59.90}.

DTO → Entity (na criação)

Quando usar: no caminho inverso, ao transformar o que o cliente enviou em algo que o ProdutoRepository sabe persistir. Como funciona: lê os campos do ProdutoRequestDTO e monta um novo Produto via builder (gerado pelo Lombok @Builder na Entity), deliberadamente sem setar id ou criadoEm — esses campos ficam sob controle exclusivo do servidor/banco.

private Produto toEntity(ProdutoRequestDTO dto) {
    return Produto.builder().nome(dto.nome()).preco(dto.preco()).build();
}
Resultado esperado

Chamado dentro de ProdutoService.criar(dto); o Produto resultante, ainda sem id, é passado para repository.save(...), que devolve a mesma entidade já com o id preenchido pelo banco.

  • Nunca use a Entity como corpo de request/response — sempre um DTO dedicado.
  • DTOs de entrada e saída podem (e costumam) ser diferentes.
  • Prefira record a classes tradicionais: menos código, imutabilidade de graça.
  • Em projetos maiores, considere MapStruct para gerar o mapeamento automaticamente.
Validação

Bean Validation

Valida os dados de entrada antes de qualquer regra de negócio rodar. Atua sobre os DTOs de requisição (seção DTO) usados pelo ProdutoController.

Anotações mais usadas

Quando usar: direto nos parâmetros de um DTO sempre que aquele campo tiver uma regra de formato a garantir antes de qualquer lógica de negócio. Como funciona: cada anotação é lida pelo Hibernate Validator (implementação padrão do Bean Validation) quando o Spring processa um @Valid — nenhuma faz algo sozinha; é a combinação com @Valid no Controller que dispara a checagem.

@NotNull            // não pode ser null
@NotBlank           // string: não pode ser null, vazia ou só espaços
@Size(min=3,max=50) // tamanho mínimo/máximo
@Email              // formato de e-mail válido
@Positive           // número > 0
@Past / @Future     // data no passado/futuro
Resultado esperado

Um @NotBlank String nome recebendo "" ou campo ausente no JSON falha a validação; um campo dentro das regras segue o fluxo normal, sem efeito visível.

Ativando a validação no Controller

Quando usar: em todo método de Controller que recebe um DTO via @RequestBody e precisa garantir que os dados cheguem válidos ao Service. Como funciona: @Valid é o gatilho — sem ele, as anotações do ProdutoRequestDTO existem na classe mas são silenciosamente ignoradas pelo Spring.

@PostMapping
public ResponseEntity<ProdutoDTO> criar(@Valid @RequestBody ProdutoRequestDTO dto) { ... }
Resultado esperado

Uma requisição com dado inválido nunca chega a executar o corpo do método: o Spring intercepta antes, lança MethodArgumentNotValidException e devolve 400 Bad Request automaticamente (ver seção Exceções para customizar essa resposta).

Validando @PathVariable / @RequestParam

Quando usar: quando o dado a validar não vem de um DTO no corpo, mas direto da URL — como um id que deveria ser sempre positivo. Como funciona: diferente de @Valid (usado em objetos complexos), @Positive aqui valida um valor simples; mas só funciona se a classe inteira do Controller estiver marcada com @Validated — sem isso, o Spring ignora validações em parâmetros soltos.

@RestController
@Validated
public class ProdutoController {
    @GetMapping("/{id}")
    public ProdutoDTO buscar(@PathVariable @Positive Long id) { ... }
}
Resultado esperado

GET /api/produtos/-5 é rejeitado com 400 Bad Request antes de chamar o Service, pois -5 viola @Positive; GET /api/produtos/5 segue o fluxo normal.

  • Sempre valide dados vindos de fora (corpo, query params, headers) — nunca confie no cliente.
  • Use mensagens customizadas e claras: @NotBlank(message = "nome é obrigatório").
  • Combine validação de formato (Bean Validation) com validação de negócio (no Service).
Exceções

Tratamento global de erros

Centraliza o tratamento de erros em vez de duplicar try/catch em cada Controller. As exceções geralmente nascem no ProdutoService e são capturadas por uma única classe: GlobalExceptionHandler.

Exceção de negócio customizada

Quando usar: para representar um erro específico do seu domínio (produto não encontrado, saldo insuficiente...), mais expressivo do que lançar uma RuntimeException genérica. Como funciona: estende RuntimeException (exceção não verificada — não obriga throws na assinatura dos métodos). Relacionado a: lançada pelo ProdutoService (seção Service, card "Buscar ou lançar exceção") sempre que um id não é encontrado.

public class ProdutoNaoEncontradoException extends RuntimeException {
    public ProdutoNaoEncontradoException(Long id) {
        super("Produto não encontrado: " + id);
    }
}
Resultado esperado

new ProdutoNaoEncontradoException(99L) cria uma exceção com a mensagem "Produto não encontrado: 99", pronta para ser capturada pelo handler global abaixo.

DTO de erro (ErroDTO)

Quando usar: como corpo de resposta padronizado sempre que o GlobalExceptionHandler precisa devolver um erro em JSON — é a versão simples de resposta de erro, alternativa ao ProblemDetail já embutido no Spring (ver último card desta seção). Como funciona: é só um record com um campo mensagem — a mesma ideia do ProdutoDTO (seção DTO), só que para representar erros em vez de produtos; por ser um record, o Jackson serializa automaticamente para JSON, sem nenhuma configuração extra. Relacionado a: usado como tipo de retorno pelos métodos @ExceptionHandler do GlobalExceptionHandler — aparece nos dois cards seguintes, "Handler global" e "Tratando erros de validação".

public record ErroDTO(String mensagem) {}
Resultado esperado

new ErroDTO("Produto não encontrado: 99") é serializado pelo Jackson como {"mensagem":"Produto não encontrado: 99"} no corpo da resposta HTTP.

Handler global

Quando usar: uma única vez por aplicação — é o ponto central que converte exceções Java em respostas HTTP consistentes. Como funciona: @RestControllerAdvice registra a classe como interceptador global; quando uma exceção do tipo declarado sobe sem ser capturada em nenhum lugar (geralmente lançada dentro de um Service), o método anotado com @ExceptionHandler correspondente é chamado automaticamente. Relacionado a: intercepta exceções vindas de qualquer Controller/Service da aplicação, incluindo ProdutoNaoEncontradoException.

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ProdutoNaoEncontradoException.class)
    public ResponseEntity<ErroDTO> tratar(ProdutoNaoEncontradoException ex) {
        return ResponseEntity.status(404).body(new ErroDTO(ex.getMessage()));
    }
}
Resultado esperado

Uma ProdutoNaoEncontradoException lançada em qualquer Service vira, para o cliente, uma resposta 404 com corpo {"mensagem":"Produto não encontrado: 99"} — sem que o ProdutoController precise saber que isso aconteceu.

Tratando erros de validação (@Valid)

Quando usar: para customizar a resposta que o Spring já devolve automaticamente ao falhar um @Valid (seção Validação), em vez de aceitar o formato padrão pouco amigável do framework. Como funciona: MethodArgumentNotValidException carrega, em getBindingResult(), a lista de campos que falharam e suas mensagens — aqui pegamos apenas a primeira; é comum agregar todas em uma lista.

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErroDTO> tratarValidacao(MethodArgumentNotValidException ex) {
    String msg = ex.getBindingResult().getFieldError().getDefaultMessage();
    return ResponseEntity.badRequest().body(new ErroDTO(msg)); // 400
}
Resultado esperado

Um POST com nome ausente devolve 400 Bad Request com corpo {"mensagem":"nome é obrigatório"} (ou a mensagem customizada da anotação do DTO).

Atalho rápido: ResponseStatusException

Quando usar: para um erro pontual, específico de um único endpoint, que não justifica criar uma classe de exceção nova nem um handler dedicado. Como funciona: pode ser lançada direto de dentro de um método de Controller ou Service; o Spring já sabe convertê-la automaticamente na resposta HTTP correspondente.

throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Produto não encontrado");
Resultado esperado

O cliente recebe 404 Not Found com a mensagem no corpo — mesmo resultado prático do handler customizado, mas sem exigir uma classe de exceção própria.

Padrão atual: ProblemDetail (RFC 9457)

Quando usar: em projetos novos, no lugar de criar um ErroDTO próprio do zero. Como funciona: desde o Spring Framework 6 / Spring Boot 3, existe um formato de erro padronizado embutido, implementando a RFC 9457 (Problem Details for HTTP APIs) — ProblemDetail.forStatusAndDetail(...) monta o objeto de resposta pronto, com título, status e detalhe.

# habilita o formato padrão em toda a aplicação
spring.mvc.problemdetails.enabled=true
@ExceptionHandler(ProdutoNaoEncontradoException.class)
public ProblemDetail tratar(ProdutoNaoEncontradoException ex) {
    ProblemDetail problema = ProblemDetail.forStatusAndDetail(
            HttpStatus.NOT_FOUND, ex.getMessage());
    problema.setTitle("Produto não encontrado");
    return problema; // Content-Type: application/problem+json
}
Resultado esperado

Resposta 404 com Content-Type: application/problem+json e corpo {"type":"about:blank","title":"Produto não encontrado","status":404,"detail":"Produto não encontrado: 99","instance":"/api/produtos/99"} — um formato já padronizado entre diferentes APIs.

  • Nunca deixe stack trace vazar para o cliente — sempre uma resposta JSON padronizada.
  • Tenha um handler "genérico" (Exception.class) como rede de segurança, devolvendo 500.
  • Em projetos novos, prefira ProblemDetail (padrão RFC 9457, já embutido) a um DTO de erro próprio — só crie um formato customizado se o time tiver um motivo específico.
Configuração

application.properties & profiles

Centraliza configurações da aplicação, separadas por ambiente. Afeta diretamente como o ProdutoRepository se conecta ao banco e como o Hibernate trata o schema das Entities.

Configurações essenciais

Quando usar: em todo projeto Spring Boot — é o arquivo padrão lido automaticamente ao subir a aplicação. Como funciona: cada propriedade configura uma parte específica do framework; spring.datasource.* configura a conexão JDBC usada por baixo dos panos pelo ProdutoRepository, e spring.jpa.hibernate.ddl-auto=validate instrui o Hibernate a apenas conferir se as classes @Entity (seção Entity) batem com as tabelas existentes, sem alterar nada.

server.port=8080
spring.datasource.url=jdbc:postgresql://localhost:5432/meudb
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.show-sql=true
Resultado esperado

Ao iniciar, os logs mostram a URL de conexão usada e, com show-sql=true, cada SQL gerado pelo Hibernate aparece no console — útil para conferir se uma query saiu como esperado.

Profiles (dev, prod...)

Quando usar: para ter configurações diferentes por ambiente (desenvolvimento, teste, produção) sem duplicar código. Como funciona: um arquivo application-dev.properties só é carregado quando o profile dev está ativo; suas propriedades sobrescrevem (ou complementam) as do application.properties padrão.

# application-dev.properties
spring.jpa.hibernate.ddl-auto=update

# ativar via linha de comando:
# java -jar app.jar --spring.profiles.active=dev
Resultado esperado

Rodando com --spring.profiles.active=dev, a aplicação usa ddl-auto=update (conveniente para desenvolvimento); sem esse profile, vale o validate mais restrito do arquivo padrão.

Lendo configurações customizadas

Quando usar: para trazer valores definidos no properties para dentro do código Java, em vez de hardcodar strings/números espalhados pelas classes. Como funciona: @Value injeta uma única propriedade por vez, lida por nome; @ConfigurationProperties(prefix = "app") faz o mesmo de forma agrupada, populando automaticamente um record inteiro a partir de todas as propriedades que começam com app. — mais organizado quando são várias.

@Value("${app.nome-empresa}")
private String nomeEmpresa;

// ou agrupando várias propriedades:
@ConfigurationProperties(prefix = "app")
public record AppProperties(String nomeEmpresa, int limitePagina) {}
Resultado esperado

Com app.nome-empresa=Acme no properties, nomeEmpresa chega preenchido com "Acme" assim que o bean é criado, sem código adicional de leitura de arquivo.

  • Segredos (senha de banco, chave JWT) sempre via variável de ambiente, nunca no código.
  • ddl-auto=update só em desenvolvimento — em produção use Flyway/Liquibase.
  • Um profile por ambiente (dev, test, prod) evita configuração condicional espalhada no código.
Migrations

Versionamento de schema (Flyway)

Controla e versiona as alterações da estrutura do banco, em vez de deixar o Hibernate criar/alterar tabelas sozinho. Garante que o schema real bata com o que as classes @Entity esperam.

Dependência

Quando usar: em qualquer projeto que use um banco real (não o H2 em memória) e precise de controle confiável sobre mudanças de schema em produção. Como funciona: o Flyway se registra como um listener que roda automaticamente antes da aplicação Spring Boot terminar de subir, checando o banco configurado em spring.datasource.* e aplicando qualquer migration pendente.

<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
Resultado esperado

Nenhum código Java adicional é necessário — a partir do próximo restart da aplicação, o Flyway já entra em ação automaticamente.

Estrutura de arquivos

Quando usar: sempre — é a convenção de nomenclatura que o Flyway espera para localizar e ordenar as migrations. Como funciona: o prefixo V1, V2, V3... define a ordem de execução; o Flyway mantém uma tabela de controle no próprio banco (flyway_schema_history) registrando quais versões já rodaram, para nunca reexecutar a mesma migration duas vezes.

src/main/resources/db/migration/
├── V1__criar_tabela_produtos.sql
├── V2__adicionar_coluna_estoque.sql
└── V3__criar_tabela_categorias.sql
Resultado esperado

Na primeira execução, o Flyway roda V1, V2 e V3 em ordem e grava cada uma em flyway_schema_history; em execuções seguintes, pula direto para qualquer versão nova adicionada depois da última já aplicada.

Exemplo de migration

Quando usar: um arquivo .sql por mudança de schema (criar tabela, adicionar coluna...) — nunca edite um já aplicado. Como funciona: o conteúdo é SQL puro, específico do banco usado; o Flyway apenas executa o arquivo como está, sem interpretar nem traduzir nada. Relacionado a: a estrutura resultante deve bater exatamente com o que a classe Produto (seção Entity) espera encontrar.

-- V1__criar_tabela_produtos.sql
CREATE TABLE produtos (
    id BIGSERIAL PRIMARY KEY,
    nome VARCHAR(120) NOT NULL,
    preco NUMERIC(10,2) NOT NULL
);
Resultado esperado

Rodar essa migration cria a tabela produtos no banco configurado, pronta para o ProdutoRepository operar sobre ela.

Configuração

Quando usar: junto com a dependência do Flyway, para desligar a criação automática de tabelas do Hibernate. Como funciona: com o Flyway ativo, o Hibernate passa a apenas validar (ddl-auto=validate) se o schema bate com as Entities, nunca criar ou alterar tabelas sozinho — quem manda no schema agora são as migrations.

spring.flyway.enabled=true
spring.jpa.hibernate.ddl-auto=validate
Resultado esperado

Se a tabela produtos não tiver, por exemplo, a coluna preco esperada pela Entity, a aplicação falha ao subir com um erro de validação de schema — sinal de que falta criar uma migration.

  • Nunca edite uma migration já aplicada em produção — crie sempre uma nova.
  • Nomeie os arquivos em ordem crescente: V1, V2, V3... o Flyway depende dessa numeração.
  • Rode as migrations automaticamente no startup — evita passos manuais de deploy.
Segurança

Spring Security & JWT

Autenticação (quem é o usuário) e autorização (o que ele pode fazer). Protege os endpoints expostos por classes como ProdutoController.

Cadeia de segurança básica

Quando usar: uma vez por aplicação — é a configuração central que decide quais endpoints exigem autenticação. Como funciona: csrf().disable() remove uma proteção pensada para formulários web com cookies (desnecessária numa API stateless com token); sessionCreationPolicy(STATELESS) impede o Spring de criar sessão HTTP; authorizeHttpRequests define regras avaliadas em ordem — aqui, tudo em /api/auth/** é público, e qualquer outra rota exige autenticação.

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.csrf(c -> c.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .anyRequest().authenticated());
    return http.build();
}
Resultado esperado

Uma requisição para /api/produtos sem token válido é barrada pelo próprio Spring Security antes de chegar ao ProdutoController, respondendo 401 Unauthorized automaticamente.

Codificação de senha

Quando usar: sempre que uma senha de usuário for salva no banco (cadastro) ou comparada no login. Como funciona: BCrypt gera um hash com salt embutido — o mesmo texto produz hashes diferentes a cada chamada de encode, e a comparação no login é feita via passwordEncoder.matches(senhaDigitada, hashSalvo), nunca comparando strings diretamente.

@Bean
public PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }
Resultado esperado

encode("123456") produz algo como $2a$10$N9qo8uLOickgx2ZMRZoMy... — mesmo com acesso ao banco, não é possível recuperar a senha original a partir desse valor.

Restringindo por papel (role)

Quando usar: quando diferentes usuários autenticados devem ter permissões diferentes (ex: só ADMIN pode deletar). Como funciona: desde o Spring Security 6, @PreAuthorize só funciona com @EnableMethodSecurity habilitado em alguma classe @Configuration — antes disso, era @EnableGlobalMethodSecurity (anotação antiga, evite em projetos novos).

@Configuration
@EnableMethodSecurity // habilita @PreAuthorize/@PostAuthorize na aplicação
public class MethodSecurityConfig { }
@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/{id}")
public void deletar(@PathVariable Long id) { ... }
Resultado esperado

Um usuário autenticado sem o papel ADMIN recebe 403 Forbidden ao chamar DELETE /api/produtos/5, mesmo estando logado — diferente do 401 (não autenticado) do card anterior.

Fluxo JWT (resumo)

Quando usar: como estratégia de autenticação padrão em APIs REST stateless. Como funciona: o cliente faz login uma vez e reutiliza o token — nenhuma sessão fica guardada no servidor; um filtro customizado (OncePerRequestFilter) intercepta cada requisição para validar o token antes de qualquer Controller ser chamado.

1. POST /api/auth/login (email + senha) → servidor gera um JWT
2. Cliente guarda o token e envia em cada chamada:
   Authorization: Bearer <token>
3. Um filtro (OncePerRequestFilter) valida o token a cada requisição
Resultado esperado

Enquanto o token não expirar, o cliente não precisa fazer login de novo a cada requisição — basta reenviar o mesmo header Authorization.

  • APIs REST devem ser stateless: nada de sessão em memória no servidor.
  • Tokens JWT devem ter tempo de expiração curto.
  • Chave de assinatura do JWT nunca deve ir para o repositório de código.
CORS

Cross-Origin Resource Sharing

Necessário quando o front-end roda em outro domínio/porta da API (ex: React em localhost:3000 chamando a API em localhost:8080).

Configuração global

Quando usar: quando toda (ou a maior parte) da API precisa ser acessível por um front-end em outra origem. Como funciona: essa configuração intercepta o cabeçalho Origin de cada requisição recebida em /api/**; se a origem bater com allowedOrigins, o Spring adiciona os headers Access-Control-Allow-* na resposta, autorizando o navegador do cliente a aceitar os dados.

@Bean
public WebMvcConfigurer corsConfigurer() {
    return new WebMvcConfigurer() {
        public void addCorsMappings(CorsRegistry registry) {
            registry.addMapping("/api/**")
                    .allowedOrigins("http://localhost:3000")
                    .allowedMethods("GET","POST","PUT","DELETE");
        }
    };
}
Resultado esperado

Uma chamada via fetch() a partir de http://localhost:3000 para GET /api/produtos funciona normalmente no navegador; a mesma chamada de outra origem não listada é bloqueada pelo próprio navegador.

CORS em um único Controller

Quando usar: útil para liberar apenas um recurso específico, sem afetar o restante da API. Como funciona: @CrossOrigin sobrescreve, só para essa classe, as regras de CORS que valeriam globalmente.

@CrossOrigin(origins = "http://localhost:3000")
@RestController
@RequestMapping("/api/produtos")
public class ProdutoController { ... }
Resultado esperado

Libera CORS apenas para as rotas de ProdutoController, mesmo que o restante da API não tenha CORS configurado globalmente.

CORS junto com Spring Security

Quando usar: sempre que o Spring Security estiver ativo (seção Segurança) e a API também precisar de CORS. Como funciona: http.cors(Customizer.withDefaults()) na cadeia de segurança faz o Spring Security respeitar a configuração de CORS já definida separadamente (via WebMvcConfigurer ou @CrossOrigin), em vez de bloquear a requisição antes mesmo dela chegar lá.

http.cors(Customizer.withDefaults())
    .csrf(c -> c.disable());
Resultado esperado

Sem essa linha, o Spring Security bloquearia a requisição antes de aplicar as regras de CORS configuradas separadamente, mesmo com a origem liberada.

  • Nunca use allowedOrigins("*") em produção junto com credenciais habilitadas.
  • Libere apenas os domínios reais do front-end (dev, staging, produção) — nunca um curinga solto.
  • CORS é aplicado pelo navegador: não substitui autenticação/autorização no servidor.
Testes

Testes automatizados

Garantem que o comportamento esperado continue funcionando conforme o código muda. Os três níveis abaixo testam, respectivamente, o ProdutoService isolado, o ProdutoController isolado, e a aplicação inteira.

Teste unitário do Service (Mockito)

Quando usar: para testar regras de negócio isoladamente, com feedback rápido. Como funciona: @Mock cria um dublê de ProdutoRepository que não conversa com banco real; @InjectMocks instancia o ProdutoService de verdade, injetando esse mock automaticamente; when(...).thenReturn(...) programa o comportamento do mock para o cenário do teste.

@ExtendWith(MockitoExtension.class)
class ProdutoServiceTest {
    @Mock ProdutoRepository repository;
    @InjectMocks ProdutoService service;

    @Test
    void deveLancarExcecaoSeNaoEncontrar() {
        when(repository.findById(1L)).thenReturn(Optional.empty());
        assertThrows(ProdutoNaoEncontradoException.class, () -> service.buscarPorId(1L));
    }
}
Resultado esperado

Roda em milissegundos, sem abrir conexão com banco nem subir o Spring; falha caso buscarPorId não lance a exceção esperada quando o produto não existe.

Teste da camada web (@WebMvcTest)

Quando usar: para testar o comportamento HTTP do Controller (status code, formato JSON) sem depender do Service real. Como funciona: @WebMvcTest(ProdutoController.class) sobe só essa fatia da aplicação (roteamento, serialização, validação); @MockBean substitui ProdutoService por um mock no contexto do Spring; MockMvc simula requisições HTTP sem abrir uma porta de rede real.

@WebMvcTest(ProdutoController.class)
class ProdutoControllerTest {
    @Autowired MockMvc mockMvc;
    @MockBean ProdutoService service;

    @Test
    void deveRetornar404() throws Exception {
        mockMvc.perform(get("/api/produtos/99")).andExpect(status().isNotFound());
    }
}
Resultado esperado

O teste falha se o ProdutoController não devolver exatamente 404 para um id inexistente (comportamento simulado pelo mock do Service).

Teste de integração completo

Quando usar: para validar um cenário real de ponta a ponta, com todas as camadas trabalhando juntas. Como funciona: @SpringBootTest(webEnvironment = RANDOM_PORT) sobe a aplicação inteira numa porta aleatória, incluindo banco (H2 em memória, seção Configuração) e contexto completo do Spring; TestRestTemplate faz uma chamada HTTP de verdade contra essa instância.

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
class ProdutoApiIT {
    @Autowired TestRestTemplate rest;

    @Test
    void deveCriarProduto() {
        var resp = rest.postForEntity("/api/produtos", novoProdutoDTO, Object.class);
        assertThat(resp.getStatusCode()).isEqualTo(HttpStatus.CREATED);
    }
}
Resultado esperado

Confirma que toda a cadeia — ProdutoController, ProdutoService, ProdutoRepository, banco — funciona junta corretamente, devolvendo 201 Created na criação bem-sucedida.

  • Teste regras de negócio, não getters/setters gerados pelo Lombok.
  • Prefira muitos testes unitários rápidos (Service) a poucos testes de integração lentos.
  • Nomeie o teste pelo comportamento esperado: deveRetornar404QuandoProdutoNaoExiste.
Documentação

Swagger / OpenAPI

Gera uma documentação interativa da API automaticamente, a partir do próprio código dos Controllers (ex: ProdutoController).

Dependência

Quando usar: em toda API que será consumida por outro time (front-end, mobile, QA) ou por terceiros. Como funciona: só de adicionar essa dependência, a biblioteca escaneia automaticamente os @RestController registrados e gera a especificação OpenAPI e a interface do Swagger UI — sem configuração extra. A versão muda com frequência: springdoc-openapi série 2.x acompanha Spring Boot 3.5.x, série 3.x acompanha Spring Boot 4.x — confira a última tag em springdoc.org antes de fixar.

<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version><!-- use a última da série 2.x (Boot 3.5) ou 3.x (Boot 4) --></version>
</dependency>
Resultado esperado

Ao subir a aplicação, os endpoints de ProdutoController já aparecem automaticamente no Swagger UI, com os parâmetros e tipos de retorno inferidos das assinaturas dos métodos.

Personalizando título e versão

Quando usar: para dar identidade à documentação gerada (nome do projeto, versão da API) em vez de ficar com o título genérico padrão. Como funciona: declarar um bean OpenAPI customizado numa classe @Configuration (ex: OpenApiConfig) sobrescreve os metadados exibidos no topo do Swagger UI.

@Bean
public OpenAPI apiInfo() {
    return new OpenAPI().info(new Info()
            .title("Catálogo API")
            .version("v1"));
}
Resultado esperado

O Swagger UI passa a exibir "Catálogo API — v1" no cabeçalho da página, em vez do título genérico padrão da biblioteca.

Documentando um endpoint específico

Quando usar: em endpoints mais importantes ou com comportamento não óbvio, que merecem uma descrição além do que o Spring já infere sozinho. Como funciona: anotações opcionais colocadas direto no método do Controller (aqui, ProdutoController.buscar) enriquecem a entrada correspondente na documentação gerada, sem exigir nenhum arquivo separado.

@Operation(summary = "Busca um produto pelo id")
@ApiResponse(responseCode = "404", description = "Produto não encontrado")
@GetMapping("/{id}")
public ProdutoDTO buscar(@PathVariable Long id) { ... }
Resultado esperado

No Swagger UI, o endpoint GET /api/produtos/{id} passa a mostrar a descrição "Busca um produto pelo id" e documenta explicitamente a possível resposta 404.

Acessando a documentação

Quando usar: após subir a aplicação localmente ou em qualquer ambiente, para explorar ou testar a API sem precisar do Postman. Como funciona: as duas URLs abaixo já ficam disponíveis automaticamente, geradas em tempo real a partir dos Controllers escaneados.

Swagger UI (interface interativa): /swagger-ui.html
JSON da especificação OpenAPI:      /v3/api-docs
Resultado esperado

Abrir http://localhost:8080/swagger-ui.html no navegador mostra uma página interativa listando todos os endpoints de ProdutoController, com botão "Try it out" para executar chamadas reais.

  • A documentação é gerada a partir do código — mantê-lo claro já mantém a doc atualizada.
  • Use @Operation e @ApiResponse nos endpoints mais importantes ou não óbvios.
  • Compartilhe a URL do Swagger UI com front-end/mobile/QA como "contrato vivo" da API.
Docker

Empacotamento e deploy

Empacota a aplicação com tudo que ela precisa para rodar da mesma forma em qualquer ambiente.

Gerar o .jar executável

Quando usar: antes de qualquer build de imagem Docker, ou para rodar a aplicação sem depender de uma IDE. Como funciona: o Maven compila o código, roda o build e empacota tudo (incluindo o servidor Tomcat embutido) em um único arquivo .jar executável.

./mvnw clean package -DskipTests
Resultado esperado

Gera target/nome-do-projeto.jar; rodar java -jar target/nome-do-projeto.jar já sobe a aplicação completa, sem precisar de um servidor de aplicação separado.

Dockerfile (multi-stage build)

Quando usar: para gerar uma imagem Docker de produção, enxuta e sem ferramentas de build desnecessárias. Como funciona: o primeiro estágio (FROM maven...) compila o projeto usando uma imagem completa com Maven e JDK; o segundo estágio (FROM eclipse-temurin...jre-alpine) parte de uma imagem bem menor, contendo só o runtime Java, e copia apenas o .jar já pronto do estágio anterior — o código-fonte e o Maven não vão para a imagem final.

FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY . .
RUN mvn clean package -DskipTests

FROM eclipse-temurin:17-jre-alpine
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java","-jar","app.jar"]
Resultado esperado

A imagem final resultante é significativamente menor do que se tudo fosse feito em um único estágio, e não expõe código-fonte nem ferramentas de build.

Build e execução

Quando usar: para testar a imagem localmente antes de enviar a um registry (Docker Hub, ECR...) ou a um ambiente de produção. Como funciona: docker build lê o Dockerfile e monta a imagem; docker run -p 8080:8080 mapeia a porta 8080 do container para a porta 8080 da máquina host.

docker build -t minha-api .
docker run -p 8080:8080 minha-api
Resultado esperado

A API fica acessível em http://localhost:8080 a partir da máquina host, rodando isoladamente dentro do container.

Configurando por variável de ambiente

Quando usar: para apontar o mesmo container Docker para bancos/ambientes diferentes, sem reconstruir a imagem. Como funciona: o Spring Boot converte automaticamente variáveis de ambiente em maiúsculas com underscore (SPRING_DATASOURCE_URL) para a propriedade equivalente do application.properties (spring.datasource.url), sobrescrevendo o valor definido no arquivo.

docker run -p 8080:8080 \
  -e SPRING_DATASOURCE_URL=jdbc:postgresql://host:5432/db \
  -e SPRING_PROFILES_ACTIVE=prod \
  minha-api
Resultado esperado

O mesmo container conecta a um banco PostgreSQL diferente do configurado no application.properties padrão, e roda com o profile prod ativo (seção Configuração).

  • Use multi-stage build: a imagem final não deve conter Maven nem código-fonte.
  • Nunca coloque senhas/segredos direto no Dockerfile — use variáveis de ambiente.
  • Configure um profile de produção (spring.profiles.active=prod) separado do de desenvolvimento.

Resumo

Boas práticas gerais de API REST

  • URLs com substantivo no plural e sem verbos: /pedidos, nunca /buscarPedidos.
  • O verbo HTTP expressa a ação (GET, POST, PUT, PATCH, DELETE) — a URL representa apenas o recurso.
  • GET, PUT e DELETE devem ser idempotentes (repetir a chamada produz o mesmo resultado final).
  • Sempre pagine listagens que podem crescer (?page=0&size=20).
  • Versione a API (/api/v1/...) antes de introduzir mudanças que quebram contrato.
  • Documente com Swagger/OpenAPI — endpoint /swagger-ui.html gerado automaticamente.
  • Libere CORS explicitamente apenas para as origens confiáveis do front-end.
  • Camadas bem separadas (Controller → Service → Repository) facilitam manutenção e testes.
  • Nunca exponha stack trace, senha ou dados sensíveis nas respostas de erro.
